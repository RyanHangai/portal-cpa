# Data Model: Recuperação de Senha e Sessão Persistente

> Baseado em `database/database.sql` e na spec 003.

## Entrada da recuperação

### SolicitacaoSenhaFormulario
| Campo | Tipo | Regras |
|-------|------|--------|
| email | texto | Obrigatorio; comparado sem maiusculas/minusculas e sem espacos nas pontas |
| nova_senha | texto | Obrigatorio; minimo de 8 caracteres |
| confirmacao | texto | Obrigatorio; igual a `nova_senha` |

## Entidades persistidas

### solicitacao_senha (tabela nova)

| Campo | Tipo | Regras |
|-------|------|--------|
| id | INTEGER identity | Gerado pelo banco |
| usuario_id | INTEGER | Obrigatorio; referencia `usuario.id` |
| nova_senha | VARCHAR | Obrigatorio; senha pretendida, guardada ate a decisao |
| situacao | SITUACAO_SOLICITACAO | Obrigatorio; padrao `pendente` |
| criado_em | TIMESTAMPTZ | Obrigatorio; padrao `NOW()` |
| decidido_em | TIMESTAMPTZ | Preenchido na aprovacao, recusa ou expiracao |
| decidido_por | INTEGER | Referencia `usuario.id` do Administrativo que decidiu; nulo na expiracao |

### situacao_solicitacao (tipo novo)
Valores: `pendente`, `aprovada`, `recusada`, `expirada`.

### Indice
`idx_solicitacao_senha_situacao` em `(situacao, criado_em)`, para a listagem de pendentes.

## Entidades em memoria

### SessaoAutenticada
Nao e persistida em tabela; vive no cookie do navegador.

| Campo | Tipo | Regras |
|-------|------|--------|
| usuario_id | inteiro | Identificador do usuario autenticado |
| login_em | data e hora em UTC | Momento do login bem-sucedido |
| assinatura | texto | HMAC-SHA256 do conteudo, conferida a cada carga de pagina |

Regras:
- Valida por 168 horas a partir de `login_em`, sem renovacao por atividade.
- Assinatura invalida, prazo vencido ou usuario inativo tornam a sessao invalida.
- O conteudo nao contem a senha.

## Transicoes de estado da solicitacao

```text
(novo pedido) -> pendente
pendente -> aprovada   (Administrativo aprova; senha do usuario e atualizada)
pendente -> recusada   (Administrativo recusa; senha permanece)
pendente -> expirada   (24 horas sem decisao; senha permanece)
aprovada, recusada, expirada -> final
```

Regras:
- Apenas a transicao a partir de `pendente` e permitida; decisoes repetidas sao ignoradas.
- Um novo pedido do mesmo usuario remove o `pendente` anterior antes de inserir o novo.
- A senha do usuario so muda na transicao para `aprovada`.

## Regras de validacao

- E-mail, nova senha e confirmacao obrigatorios.
- Nova senha com no minimo 8 caracteres.
- Confirmacao igual a nova senha.
- E-mail sem conta ativa nao gera solicitacao.
- Mensagem exibida e a mesma para e-mail existente e inexistente.

## Fluxos

### Registrar pedido
1. Normalizar o e-mail.
2. Validar os campos.
3. Buscar o usuario ativo pelo e-mail; se nao existir, encerrar sem gravar nada.
4. Remover o pedido `pendente` anterior do usuario.
5. Inserir a solicitacao com `situacao = 'pendente'`.

### Listar pendentes (Administrativo)
1. Marcar como `expirada` as solicitacoes `pendente` com mais de 24 horas.
2. Retornar as solicitacoes `pendente`, com e-mail do solicitante e `criado_em`.

### Aprovar
1. Atualizar a solicitacao de `pendente` para `aprovada`, gravando `decidido_em` e
   `decidido_por`.
2. Se nenhuma linha foi atualizada, encerrar (decisao ja tomada).
3. Atualizar `usuario.senha` com a `nova_senha` guardada.
4. Confirmar a transacao.

### Recusar
1. Atualizar a solicitacao de `pendente` para `recusada`, gravando `decidido_em` e
   `decidido_por`.
2. Nenhuma alteracao em `usuario`.

## Schema (trecho novo de `database/database.sql`)

```sql
CREATE TYPE "situacao_solicitacao" AS ENUM (
	'pendente',
	'aprovada',
	'recusada',
	'expirada'
);

CREATE TABLE IF NOT EXISTS "solicitacao_senha" (
	"id" INTEGER NOT NULL UNIQUE GENERATED BY DEFAULT AS IDENTITY,
	"usuario_id" INTEGER NOT NULL,
	"nova_senha" VARCHAR NOT NULL,
	"situacao" SITUACAO_SOLICITACAO NOT NULL DEFAULT 'pendente',
	"criado_em" TIMESTAMPTZ NOT NULL DEFAULT NOW(),
	"decidido_em" TIMESTAMPTZ,
	"decidido_por" INTEGER,
	PRIMARY KEY("id")
);

ALTER TABLE "solicitacao_senha"
ADD FOREIGN KEY("usuario_id") REFERENCES "usuario"("id")
ON UPDATE NO ACTION ON DELETE NO ACTION;

ALTER TABLE "solicitacao_senha"
ADD FOREIGN KEY("decidido_por") REFERENCES "usuario"("id")
ON UPDATE NO ACTION ON DELETE NO ACTION;

CREATE INDEX "idx_solicitacao_senha_situacao"
ON "solicitacao_senha" ("situacao", "criado_em");
```

> `database/database.sql` continua sendo a unica fonte do schema; nao ha script de
> migracao. Bancos criados antes desta feature precisam de volume novo.
